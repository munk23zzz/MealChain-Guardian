### 2a. Mengapa tidak dipisah ke database tes sendiri (dicoba & ditolak)

Agar tidak bergantung pada jendela sepi, sempat dipertimbangkan menjalankan
suite di database terpisah. Hasil penelusuran: **belum bisa tanpa mengubah infra
tes**, karena

- URL DB tes di-*hardcode* di `backend/tests/conftest.py` pada empat tempat
  (`postgresql+psycopg://…@postgres:5432/mealchain`); tidak ada pembacaan env.
- `app.core.config.settings.database_url` **tidak** ditimpa oleh conftest, sehingga
  aplikasi di dalam `TestClient` tetap menulis ke DB demo yang sama. Mengarahkan
  fixture ke DB lain tanpa menimpa settings hanya akan membuat fixture dan
  aplikasi memakai DB berbeda — hasilnya gagal palsu jenis baru.

Karena itu isolasi DB **tidak** dikerjakan pada sesi ini: nilainya kecil
dibanding risiko menyentuh `conftest.py` saat sesi lain sedang memakainya. Kalau
kelak dibutuhkan, urutannya: (1) conftest membaca `TEST_DATABASE_URL`, (2) set
`settings.database_url` di fixture session sebelum `TestClient` dibuat,
(3) `CREATE DATABASE mealchain_iso TEMPLATE mealchain` atau `pg_dump | psql`,
(4) verifikasi bahwa hasil di DB kembar sama dengan DB demo (fixture seed ikut
terbawa template).

## 3. Determinisme `tests/shipment-timeline.test.ts` (pertanyaan awal W-4)

Klaim "gerbang flaky karena waktu" **dibatalkan oleh bukti**:

- Fixture tes memakai stempel waktu ISO **tetap** (`2026-10-16T12:24:00+00:00`, `2026-11-07T11:00:00+00:00`);
  `grep -c "Date.now\|new Date(" tests/shipment-timeline.test.ts` → **0**.
- Modul yang diuji (`lib/shipment-timeline.ts`) murni: hanya mengurutkan
  `Date.parse(at)` dari data server, tidak membaca jam sistem.
- Run-1 yang merah terjadi karena berkas tesnya **disunting pukul 00:49:50 saat
  run dimulai 00:49:35** (mtime vs waktu mulai) — artefak suntingan bersamaan.
- Setelah itu suite frontend hijau berulang kali: **887/887** (17 Okt dini hari),
  **1080/1080** (setelah W-2), **1127/1127** (setelah W-3).

Karena tesnya **tidak** bergantung waktu, tidak ada perubahan kode yang dilakukan
untuk "menstabilkannya" — mengubah tes yang benar hanya akan menyembunyikan
penyebab sebenarnya. Yang dilakukan: memastikan setiap run dicatat bersama
keadaan repo saat itu (bagian 1–2).
